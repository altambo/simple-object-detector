# SimpleObjectDetector

A serverless web app that finds objects in photos. Upload an image (or paste an image URL) on a static web page, and a YOLOv8 model running on AWS Lambda returns the image with labelled boxes and a summary such as *"Found 5 objects: 4 person, 1 bus."*

It detects the 80 everyday object classes of the [COCO dataset](https://cocodataset.org) (people, vehicles, animals, furniture, food and so on), keeping detections with confidence above 0.25.

## How it works

```
                    ┌─▶ CloudFront (HTTPS) ──▶ private S3 bucket: index.html, main.js, config.js
                    │
Browser ────────────┼─▶ POST /          ──▶ GetImageUrlFunction ──▶ S3 uploads + DynamoDB + SQS
                    │                                                                    │
                    │                                                                    ▼
                    │                                    ProcessImageFunction (ONNX Runtime container)
                    │                                    detect → upload annotated image → DynamoDB
                    │                                                                    │
                    └─▶ GET /{imageId}  ──▶ SODCheckJobStatus ◀── DynamoDB ◀─────────────┘
                        (every 2 s)         (status, summary, 15-minute link to the result)
```

1. The page is served over HTTPS by CloudFront from a private S3 bucket.
2. **`POST /`** (API Gateway → `GetImageUrlFunction`) stores an uploaded image in the private uploads bucket (or records the image URL), creates a job in DynamoDB and puts it on an SQS queue.
3. **`ProcessImageFunction`** handles each job in its own invocation (several can run in parallel): it downloads the image, runs detection, uploads the annotated image and writes the summary and a 15-minute presigned link to DynamoDB. Jobs that crash or time out 3 times move to a dead-letter queue.
4. The page polls **`GET /{imageId}`** (`SODCheckJobStatus`) every 2 seconds and shows the result when the job completes.

### Performance

Measured on Lambda (x86_64, 3008 MB):

| | Time |
|---|---|
| Processing a warm request | ~1–1.5 s |
| Cold start (first request after the function has been idle) | ~5.5 s |
| First request after a new deploy | 15–30 s (Lambda caches the new container image once) |

The processor runs the model with ONNX Runtime, numpy and Pillow only. Leaving out PyTorch and Ultralytics keeps the container image at ~350 MB and roughly halves cold starts.

## Project layout

```
backend-container/   ProcessImageFunction: Dockerfile, app.py (Lambda handler), detector.py (YOLOv8 inference), yolov8m.onnx (Git LFS)
backend-lambda/      get_image_url.py (POST /) and check_image_status.py (GET /{imageId})
frontend/            index.html, main.js; config.js is generated by deploy.sh (see config.example.js)
template.yaml        All AWS resources (AWS SAM)
deploy.sh            Build, deploy and upload the frontend
tests/               Unit tests (pytest, AWS mocked with moto)
scripts/             test_container.sh: tests the container image with the Lambda runtime emulator
infra/               One-time IAM role for deploying from GitHub Actions
docs/ci-cd.md        CI/CD setup
```

All AWS resource names include the environment (`dev`, `prod`), so several stacks can coexist in one account.

## Prerequisites

1. **AWS CLI v2**, configured with credentials (`aws configure`): [install guide](https://docs.aws.amazon.com/cli/latest/userguide/getting-started-install.html)
2. **AWS SAM CLI**: [install guide](https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/install-sam-cli.html)
3. **Docker**, running: SAM builds the Lambda packages and the container image with it.
4. **Git LFS**: the model weights (`backend-container/yolov8m.onnx`, ~100 MB) are stored with [Git LFS](https://git-lfs.com). Install it before cloning, or run this after cloning:
   ```bash
   git lfs install
   git lfs pull
   ```

## Deploy

```bash
./deploy.sh dev    # default
./deploy.sh prod
```

The script:
1. Clears the local `.aws-sam/` build cache.
2. Validates and builds the SAM template.
3. Deletes the stack first if it is stuck in `ROLLBACK_COMPLETE` / `ROLLBACK_FAILED`.
4. Runs `sam deploy` to stack `SimpleObjectDetector-<env>` in `us-east-1` (edit `REGION` in `deploy.sh` to change it). SAM creates the S3 bucket and ECR repository it needs for packaging.
5. Writes `frontend/config.js` from the stack outputs.
6. Uploads `index.html`, `main.js` and `config.js` to the website bucket and invalidates the CloudFront cache so the new files are served immediately.

When it finishes, it prints the website URL (`https://<id>.cloudfront.net`) and the API endpoint. On the first deploy, creating the CloudFront distribution adds several minutes.

If you stop the script after confirming the changes, CloudFormation keeps deploying in AWS. Wait for the stack to finish, then run the script again so it uploads the frontend.

## Using a different model

`detector.py` works with any YOLOv8-style detection model exported to ONNX by Ultralytics; it reads the input size and class names from the model file. For example, the smaller and faster `yolov8n`:

```bash
pip install ultralytics
yolo export model=yolov8n.pt format=onnx    # writes yolov8n.onnx
```

Replace `backend-container/yolov8m.onnx` with the exported file, keeping the name `yolov8m.onnx` (the `Dockerfile`, `app.py` and tests refer to it), then redeploy. A smaller model may find fewer objects in the test photo, so check `python -m pytest` and adjust `tests/test_detector.py` if needed.

## Local development and testing

Install the dev dependencies (Python 3.14 recommended, to match Lambda):

```bash
pip install -r requirements-dev.txt
```

- **Unit tests:** `python -m pytest`. AWS is mocked, so no account or credentials are needed.
- **Container test:** `./scripts/test_container.sh` builds the processing image and tests it with the Lambda runtime emulator (needs Docker).
- **Template check:** `sam validate --lint`.
- **Running handlers against real AWS resources:** copy `.env.example` to `.env` and fill in the names of deployed resources.

## CI/CD

GitHub Actions runs the unit tests, the SAM template lint and the container test on every pull request and push to `main`. Deploys run from **Actions → Deploy** and only proceed if CI passes. See [docs/ci-cd.md](docs/ci-cd.md) for the one-time setup (AWS role via OIDC, GitHub environments).

## Removing a deployment

S3 buckets must be empty before CloudFormation can delete them:

```bash
ENV=dev
aws s3 rm "s3://simpleobjectdetector-${ENV}-frontend-bucket" --recursive
aws s3 rm "s3://simpleobjectdetector-${ENV}-uploads-bucket" --recursive
aws cloudformation delete-stack --stack-name "SimpleObjectDetector-${ENV}"
```

Deleting the CloudFront distribution can make this take 10–15 minutes. Log groups are deleted with the stack.

## Security and cost notes

- **The API is unauthenticated.** Anyone with the URL can submit images, and each job runs a 3 GB Lambda for up to 60 seconds. API Gateway throttling limits the rate of uploads, but set up an [AWS Budgets](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html) alert, and add authentication if you keep a deployment public for long.
- Uploaded images and results are stored in a private bucket, shared with the browser only through 15-minute presigned links, and deleted after 7 days.
- Image URLs submitted by users are only fetched over `http`/`https` from public IP addresses, with a 10 MB size limit and a 10-second timeout.
- The repository contains no credentials. Deployment uses your AWS CLI credentials, and each Lambda has an IAM role limited to the stack's own resources.
- `frontend/config.js`, `.env` and `samconfig.toml` are git-ignored because they contain deployment-specific values.
